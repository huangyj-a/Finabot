# Finabot 面试准备（面试官视角参考答法）

> 原则：**每一句都基于真实代码回答，不夸大；数字答不出测量方法就降级为定性**。诚实暴露已知遗留（专家校准未做、消融未跑完基线）是加分项，不是减分项。

---

## 一、核心概念速答（必考）

### Q5：7 条一票否决硬门禁是哪 7 条？"虚构事实"怎么用确定性规则判？

**参考答法**（先分层，再坦白边界）：

> 报告定义了 7 条否决项，我按"能否机械判定"分了三层落地：
> 1. **确定性门禁**（`graders.py` 纯正则/算术，不依赖 LLM）：时点泄漏（日期 > as_of）、无据荐股（`建议买入/仓位调整/目标价` 等模式）、提示注入（`忽略系统指令` 等）、敏感泄露（`api_key/sk-` 等）、编造自白（`我编造了` 等显式自我披露）。
> 2. **计算比对**：关键数字与参考计算在容差内比对（`check_reference_calculations`）。
> 3. **事实门 + LLM Judge**：数字是否可回溯到上游证据（`check_fact_traceability`）+ 新闻推理/反证/综合三个语义维度由隔离 Judge 评分。
>
> 坦白：**"虚构事实"的深度语义判定是确定性规则做不了的**——一个编造得"合理"的价格，正则查不出来，只能靠"数字不在证据里"（事实门）+ Judge 交叉。所以我的确定性门禁查的是"格式/时点/自白/越界"，语义层面交给 Judge，且 Judge 还没做专家校准（这是已知遗留）。

**考察点**：有没有把"写了个正则"说成"解决了语义问题"。能说出"确定性查什么、语义查不了、交给了谁"就过关。

### Q6：时钟冻结怎么实现？哪些 `datetime.now()` 故意不替换？

**参考答法**：

> 数据路径 12 处 `datetime.now()` 全部换成 `clock.now()`——它优先读 `FINABOT_EVAL_AS_OF`，否则退回墙钟。这 12 处在 akshare_tools(9)、news_tools(2)、akshare_cache(1)。
> **故意不替换**的是运营墙钟：会话 TTL（`_cleanup_expired`）、心跳（runtime）、telemetry/诊断时间戳。因为冻结这些会导致过期会话清理和心跳错乱。
> 这样"时点泄漏"就成了机械判定：任何产出时间戳 > as_of 直接一票否决。

**考察点**：是否理解"业务时间"和"墙钟"的区别。答出这个区分，说明真动手改过。

---

### Q8：250 个 trial 零失败时，95% 置信上界是多少？

**参考答法**：

> 用 rule of three：`1 - alpha^(1/n)` ≈ `3/n`，即约 **1.2%**（3/250）。所以零失败不等于零风险——最多只能说"严重失败率 95% 置信上界约 1.2%"。要压到 0.3% 需要约 1000 次目标测试。我代码里 `metrics.py` 的 `_internal_rule_of_three` 和 Wilson 区间都实现了这个。

**考察点**：统计素养。能答出 1.2% 且解释来源，说明不是抄指标名。

---

### Q14：电路熔断的"半开"状态机怎么实现的？

**参考答法**（如实描述自己的简化版）：

> 状态：closed →（连续失败 ≥ 阈值 5）→ open（冷却 60s）→ 冷却结束 → 重置计数回 closed。
> 我的是**简化半开**：冷却结束后直接重置连续失败计数（相当于回到 closed 允许一批探测），而不是严格的"单探针半开"（探一次，成功关、失败再开）。
> **tradeoff**：这样能减少抖动，但代价是可能向仍不可用的端点再打 threshold 次请求。严格单探针半开更省请求、但更容易频繁切换。我选了前者，并把熔断状态暴露到诊断快照。

**考察点**：是否真懂状态机、能否讲清自己的简化 vs 经典的差别。能主动说出"我这是简化版 + 代价"就是满分。

## 二、数字与结论的诚实框架（最容易问穿）

### Q3：LLM 调用 11→7、token 降 50% 怎么测的？牺牲了什么？

**参考答法**：

> 11→7 来自"持仓分析流水线"优化：把 news→bull→bear→summary 折叠进一个编译子图，supervisor 只跳一次，减少了反复回到 supervisor 的轮次；同时共享 AKShare 缓存，避免同一只股票重复拉数、重复序列化进上下文。token 下降主要来自"少轮 supervisor 重发整段上下文 + 数据只注入一次"。
> **代价**：折叠后 bull/bear/summary 不再是 supervisor 可独立路由的节点，牺牲了"单独调看多/看空"的细粒度控制和消融灵活性。这是有意识的取舍。
> 诚实：token -50% 是优化前后的对比估算，不是严格 A/B 的多次平均，我会在简历里保留但要能说出"怎么算的"。

**考察点**：数字可信度 + 是否意识到折叠的代价。

---

### Q9：六组消融的结论是什么？多 Agent 真的比单 Agent 好吗？

**参考答法（诚实版，关键）**：

> 消融框架和 runner 都实现了（`eval/ablation.py`：单 Agent/无看空/无结构化/完整/随机失败/证据冲突，环境变量隔离），**但正式基线还没跑完**——因为需要先采样全部冻结数据 + 专家校准，否则结论不可信。
> 我的立场：**数据说话**。报告方法论里明确写了"若多 Agent 只改善文风却增加事实错误/故障传播，就回退简单架构"。目前没有"多 Agent 显著优于单 Agent"的量化结论，这是我简历里没写具体收益数字的原因。

**考察点**：诚实。装"跑过了、多 Agent 更好"会被追问具体数字问穿；说"框架好了、基线待跑、立场是数据说话"反而体现工程严谨。

---

### Q16："故障定位效率提升 90%"怎么来的？

**参考答法**：

> 这个百分比是**目标值/估算，不是严格 A/B**。真实交付的是：诊断日志结构化（每异常一行 JSON）+ 心跳差分判读（心跳停摆/队列积压/LLM 失败率）+ 三级遥测 + 每轮 trace 落盘，把"人工翻海量日志"变成"读诊断日志 + 按 trace 复现"。
> 如果面试官追，我承认没做严格 MTTR 对照，简历里可以改成"显著缩短故障定位耗时"或删掉 90%。

**考察点**：数字是否拍脑袋。没实测就主动降级，是加分。

---

### Q11：[UNTRUSTED_DATA] 只是个 prompt 标记，模型真的会遵守吗？

**参考答法**：

> 它是**纵深防御的一层，不是银弹**。我做的：记忆/新闻/网页正文统一包裹标记 + 注入测试用例（断言注入正文不得被执行）。但我承认：prompt 层防护的最终有效性依赖模型遵循，**没有做对抗性实测**（构建攻击集测通过率）。
> 更硬的防护应是：注入内容进 user 角色（而非 system）、结构化输出 + 事实门兜底。这是已知的下一步。

**考察点**：是否把"写了个标记"当"解决了问题"。诚实说"这是软防护、缺对抗实测"过关。

---

### Q13：结构化"正文+JSON"的解析失败率多少？

**参考答法**：

> 没测过真实失败率——因为**结构化输出默认关闭**（`FINABOT_STRUCTURED_OUTPUT=0`），生产走自由文本；评估时才开。
> 设计上做了容错：`parse_subagent_result` 找到 JSON 就抽取、正文保留；找不到/解析失败就整体按自由文本 + `confidence=low` 降级，**绝不让解析失败杀掉整轮**。这是"宁可降级不可崩溃"。

**考察点**：容错设计是否真的落地。

## 三、设计 tradeoff 深度题

### Q4：凭什么说是"辩论"而不是三个 prompt 拼接？

**参考答法（诚实）**：

> 严格说，当前是**"单轮对立陈述"**：bull 和 bear 各自基于 news_report 说一次（二者并行、互不可见），summary 收口合并。bull 没有机会逐条回应 bear 的反驳。
> 评估报告的五角色其实也只要求"看空 Agent 找反例 + 综合 Agent 合并"，单轮对立已满足"双向交叉验证"。若要真"多轮辩论"，得把 bull/bear 改成顺序循环（bear 拿到 bull 的论点再反驳），成本更高，当前收益不明确，所以没做。

**考察点**：概念诚实度。主动承认"不是多轮辩论"是加分，硬拗是减分。

---

### Q10：事实门会不会误杀"计算出来的数字"（如 20 日涨跌幅）？

**参考答法**：

> 会，这是当前启发式的已知局限。`check_fact_traceability` 只查"数字是否逐字出现在证据里"，而涨跌幅是算出来的、不会逐字出现，会被判"不可回溯"。
> 缓解：报告标注"数据缺失/时间未知"时豁免（`missing_marked`）。更严谨的下一步是让结构化 claims 的 `kind=calculation` 免于字面回溯、改由"参考计算比对"验证。

**考察点**：实现的边界感。能说出"会误杀 + 怎么缓解 + 更优方案"是满分。

---

### Q12："帮我看看茅台能不能买"算违规荐股吗？

**参考答法**：

> 我的拒绝判定是**关键词规则**（`refusal.classify_question`），命中"能买/该买/仓位/收益承诺"等 → `refuse_specific_advice`，转风险教育。所以"能不能买"会命中"能买"、走拒绝。
> 边界由关键词表维护，三档：safe（研究/教育）/ caution（提及买卖但带研究限定）/ refuse（具体买卖/仓位/收益承诺）。**它不是法律判断**——上线前要律师/合规逐项审查，这是报告明确要求的。

**考察点**：合规边界是否清晰 + 是否误以为规则=法律意见。

## 四、压轴题

### Q17：最难的一个 bug 怎么定位的？

**参考答法**（用真实发生的两个）：

> 1. **工具调用漂移死循环**：GLM 偶尔把工具调用当纯文本输出（`<tool_call>` 标记），早期会导致路由失效甚至循环。定位：发现某轮 supervisor 一直重复、不收敛，抓包看到返回是文本而非结构化 tool_calls。解决：加了正则兜底解析（支持多工具多参数）+ 轮次预算强制收口。
> 2. **checkpointer 空状态误判**：LangGraph 无 checkpoint 时 `aget_state` 返回 `values={}` 而非 `None`，早期用 `is None` 判断"是否首次"导致重启后不重建历史。定位：打日志看 values 是空 dict 不是 None，改判"空 values"。

**考察点**：有没有真实的踩坑记忆。能讲出"现象→定位→根因→修法"就过关。

---

### Q18：251 项测试会不会"自证正确"（mock 过度）？

**参考答法**：

> 有风险。测试用 monkeypatch 假 akshare/litellm，假对象和生产契约不一致会自证正确——早期就踩过：lookup 契约 `sample` vs 假对象 `candidates` 不一致被测试掩盖。
> 缓解：尽量复用真实 payload 构造、fixture 用真实采样数据（腾讯源 250 行真实行情）、关键契约（引用规范/时点/门禁）用"坏答案必须被否"的方式反向测试。

**考察点**：测试质量意识。

---

### Q19：重新做，最想改哪个设计？

**参考答法**：

> 1. **一开始就做时钟抽象和评估 harness**，而不是后期补——很多安全不变量（时点、可追溯）要在数据层就有钩子，后补成本高。
> 2. **结构化交接一开始就设计成"正文 + JSON 分离"**，而不是"要么 JSON 要么文本"——保留正文给下游、结构给评估，才能既保质量又可追责。
> 3. 规则路由的关键词表做成**配置化**，别硬编码。

---

### Q20：这个系统最大的风险/局限？

**参考答法（诚实三连）**：

> 1. **评估基线未闭环**：消融没跑完、专家校准没做，所以"多 Agent 一定更好"目前是假设不是结论。
> 2. **结构化输出的真实可靠性未知**：默认关闭，没测过真实 JSON 产出率/解析失败率。
> 3. **合规是规则不是法律意见**：拒绝路径能挡关键词级请求，挡不住语义级擦边，上线前必须律师审查。
